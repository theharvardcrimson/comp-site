{% comment %} Two perpetually moving bands, opposite directions: the ten board names on top, front pages below. Both are pure decoration -- no links, no interaction, aria-hidden. That is what keeps them clear of WCAG 2.2.2: they convey no information that isn't already a static list further down the page, and nothing here is reachable only through moving content. Every board is a real row in the index below and in the drawer. Each band prints its list twice so translateX wraps with no visible gap. prefers-reduced-motion stops both outright. The covers are NOT lazy-loaded, deliberately. Both passes point at the same URLs, so laziness saves nothing once the band is reached -- and the band sits directly under the hero, so essentially every visitor reaches it. With loading="lazy" the duplicated second pass measured 1 of 6 copies painted after scrolling the band into view and waiting: the copies stay outside the viewport horizontally, so the load never triggers, and the loop would wrap onto blanks. Because nothing here is lazy, srcset does the saving instead, and with twenty covers it matters: the 292px-wide files total 848KB, the 156px ones 316KB. A phone displays each cover at 78px and must not pay for desktop pixels -- most of this site's traffic and nearly all its signups are phones. `sizes` states the real display width, 78px below 750px wide and 146px above, which is where .press-item's height clamp stops growing. Do NOT add width/height attributes to these. They map to presentational hints for the CSS width/height properties, and an explicit width beats aspect-ratio, so .press-item's `height: clamp(...) + aspect-ratio: 25/48` stopped deriving the width: every cover rendered 292px wide instead of 146px while srcset still picked the file for 146px, i.e. twice the size and blurry. There is no layout-shift argument for adding them either -- CSS already fixes the height and the ratio supplies the width before the image loads. Board names use `name`, not `display_name`: no "(Flyby)" or "(FM)" here.
